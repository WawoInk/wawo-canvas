# 数据库结构

后端使用 PostgreSQL 和 GORM。本文记录需要跨模块理解的核心表；字段以 `model/` 中的结构为准。

## enterprises 与 users

`enterprises` 保存企业名称、`active/disabled` 状态、唯一主账号 ID 和 `numeric` 类型的 `discount_rate` 折扣倍率。倍率默认 `1`，数据库约束范围为 `0.1-1`。企业和主账号在同一个 PostgreSQL 事务中创建；延迟外键与约束触发器在事务提交时保证主账号存在、属于当前企业且企业身份为 `owner`。

`users` 的平台角色仍为 `guest/user/admin`。企业归属使用可空的 `enterprise_id` 和 `enterprise_role` 表达，企业身份只允许 `owner/member`：

- 无企业账号的两个字段均为空；企业账号的两个字段必须同时存在。
- `enterprise_id + owner` 使用部分唯一索引，保证一个企业最多一个主账号。
- 一个账号只有一个 `enterprise_id`，第一版不支持跨企业或多企业成员关系。
- `session_version` 默认从 1 开始；密码重置递增版本，使旧 JWT 立即失效。
- 企业成员查询和修改同时限定当前主账号的 `enterprise_id` 与 `enterprise_role = member`，不能通过用户 ID 操作主账号、个人用户、平台管理员或其他企业成员。

企业或成员禁用不删除数据。认证中间件每次从数据库读取当前用户和企业状态，因此禁用会立即拒绝已有会话和新登录；成员密码重置会递增 `session_version`。

## credit_logs 与企业积分

`users.credits`、`credit_logs.amount/balance`、`generation_tasks.credits/upstream_credits/billing_rate` 和 `enterprises.discount_rate` 均使用 PostgreSQL `numeric` 保存完整小数精度。数据库启动初始化会在 `AutoMigrate` 前显式、可重复地把已有非 `numeric` 计费列转换为 `numeric`。

平台管理员调整企业主账号积分时，`users.credits` 更新与一条 `credit_logs` 记录在同一个 PostgreSQL 事务中完成。事务会锁定目标主账号行，按 `delta` 增减余额，并在扣减后余额小于 0 时整体失败，因此并发调整不会覆盖其他请求的结果。

平台调整流水使用 `admin_adjust` 类型：`user_id` 记录目标主账号，`related_id` 记录操作的平台管理员，`amount` 记录增量，`balance` 记录本次变动后的余额，`remark` 记录调整原因。

企业主账号向成员分配积分使用 `enterprise_allocate`，收回积分使用 `enterprise_reclaim`。每次操作在同一个事务中锁定主账号和目标成员，更新双方 `users.credits`，并写入两条共享 `related_id` 的流水；`counterparty_id` 记录对方账号，`amount` 使用双方各自视角的正负值，`balance` 保存本次变动后的余额。

`users.credits` 具有非负检查约束。企业积分流水对 `user_id + type + related_id` 建立部分唯一索引，仅作用于分配和收回类型，用于保证客户端请求 ID 幂等；余额不足、流水写入失败或并发竞争时整个事务回滚。

企业汇总流水不新增账本表：查询从当前主账号推导 `enterprise_id`，通过 `credit_logs.user_id` 关联当前企业的 `owner/member`，并在数据库查询中完成成员、类型、关键词和分页筛选；其他企业、个人用户和平台管理员的流水不会进入结果。

兼容 AI 代理的 `ai_consume/ai_refund` 也在锁定用户行后，于同一事务更新余额并写入流水；因此生成扣费、退款和企业划拨会按同一用户串行结算，普通资料或登录信息保存不会写回陈旧积分。企业主账号和成员按 `原始积分 × discount_rate` 精确扣费，不再向上取整，例如 `5 × 0.5 = 2.5`；个人用户与平台管理员等价于倍率 `1`。退款按同任务已落账的消费流水原额返还，不受后续倍率调整影响。

管理员修复失败或取消任务的缺失退款时，服务端只接受已有 `ai_consume` 流水的任务，并从该流水恢复实际扣费账号（包括企业成员）的原额；操作员和原因写入 `ai_refund.related_id/remark`。任务已存在退款流水时重复请求直接幂等成功，任务处于运行中或没有消费流水时拒绝补发。该操作不经过企业主账号划拨，也不改变现有 `enterprise_allocate/enterprise_reclaim` 语义。

## assets、user_files 与企业共享媒体

`assets.enterprise_id` 为空时是现有个人素材，继续由 `user_id` 表达个人所有权；个人素材查询、更新、删除和同步都显式限定 `enterprise_id IS NULL`。`assets.enterprise_id` 非空时是企业共享素材，`user_id` 记录创建者账号，`type` 可为 `text/image/video`，图片和视频通过 `file_id` 关联企业文件。

`user_files.enterprise_id` 为空时是个人文件；个人文件接口同样显式限定企业字段为空，因此企业主账号即使与文件创建者是同一用户，也不能通过个人文件接口读取、下载或删除企业文件。非空时文件属于企业，`user_id` 记录上传者，企业文件对象 Key 只保存在服务端。

企业列表、详情和文件读取始终以当前认证账号推导出的企业 ID 查询；客户端提交的 `enterpriseId`、`userId`、素材 ID 或文件 ID 不参与授权范围。主账号可上传、替换和删除企业媒体；有效主账号和成员可读取、预览和下载。文件的读取、下载、预签名、更新和删除分别校验权限，企业或成员停用后不再签发新的 URL。

企业媒体按需返回短期预签名 URL，API 不返回原始 S3 Key。企业素材使用独立 API 按需读取，不进入个人素材 Zustand store、IndexedDB 增量同步或 WebDAV 清单；删除企业素材时同步移除其关联企业文件记录。

企业素材复制不复用源 `assets.id` 或 `user_files.id`。文本复制直接创建 `enterprise_id IS NULL` 的个人素材；媒体复制先由对象存储服务端生成个人对象，再在一个 PostgreSQL 事务中写入个人 `user_files` 和 `assets`，两条记录的 `user_id` 都是当前认证账号。事务失败时回滚数据库记录并删除新对象；源企业素材或企业文件删除后，个人副本仍按个人文件和个人素材权限读取。

## storyboard_projects 与可变 Storyboard Workspace

`storyboard_projects` 是可变 Storyboard Workspace 的聚合根，保存当前账号所有权、标题、原始剧本、生成选项、模型、`source_hash`、`draft/ready` 状态、验证摘要、场景/镜头计数、项目级 `revision`，以及由 `artifact_file_id` 指向 `user_files` 的私有 JSON artifact 引用；`artifact_hash` 保存规范化 artifact 的 SHA-256，用于内容未变化时复用已有文件。项目创建时 `revision=1`；更新必须提交当前 `expectedRevision`，成功后 revision 加 1，旧 revision 返回 HTTP 409 和最新完整项目，不做字段级自动合并。更新和重新生成保留 Project ID 与原始 `created_at`。

`status` 只表达 Workspace 是否已有 Storyboard Document：没有 Document 为 `draft`，存在 Document 为 `ready`。校验通过或失败继续由 `validation_status` 表达，不能混入 Workspace status。`directorPlan`、`document` 和 `validation` 不拆成数据库表，而是统一保存为 `storyboards/{user_id}/{entity_id}/{file_id}.json`；创建时省略的复杂字段规范化为 JSON `null`。Scene、Segment、Shot 的非空稳定 UUID 保存在 Document 内：首次保存会替换模型给出的缺失、重复或不可信 ID，更新或重新生成时优先复用请求中已经属于当前 artifact 的稳定 ID；缺失或不可信 ID 再按父级内的 `sceneNo`、`segmentNo`、`shotNo` 匹配未被其他实体保留的旧 ID，新实体生成新 UUID。

artifact 变化时，服务端先上传新对象，再在同一 PostgreSQL 事务中创建新的 `user_files`、按 `id + user_id + expectedRevision` CAS 更新项目引用/摘要/revision，并删除旧文件记录。事务或 CAS 失败时补偿删除新对象，旧可用 artifact 始终保持引用；事务成功后再 best-effort 删除旧对象。规范化后的 artifact 未变化时可复用旧文件，只更新元数据和 revision。删除项目时同步清理项目与文件记录，再 best-effort 删除对象。

所有列表、详情、更新和删除查询都使用当前认证账号限定 `user_id`，API 不返回原始 S3 Key、公开 URL 或可长期复用的预签名地址。同账号可通过服务端 API 在不同会话或设备恢复并继续编辑分镜项目；Brainstorm Conversation、Message 和 Project Memory 使用下述独立表与 API 持久化，但 Canvas 关联、我的素材或其他浏览器本地数据不因此统一云同步。

## Storyboard Brainstorm 持久化表

Storyboard Brainstorm 使用且只使用三张子表，不新增 Conversation revision、Project `activeConversationId`、Summary 字段、Turn ledger、Tool 表、GIN/vector 索引或外键框架。当前范围是后端持久化与并发边界，不代表模型调用、Summary、Context Builder、Tool Executor、前端 UI、Canvas 关联或真实浏览器验证已经完成。

### storyboard_brainstorm_conversations

| 字段 | 说明 |
| --- | --- |
| `id` | 客户端提供的稳定非空 Conversation ID |
| `user_id`、`project_id` | 当前账号与父 Storyboard Project；所有读写同时限定 |
| `title` | 会话标题；空标题默认“新对话” |
| `current_message_id` | append、regenerate 或 continue 最近选中的 Message |
| `created_at`、`updated_at` | 创建与更新时间 |

Conversation 不保存独立 revision。Turn 写入通过 PostgreSQL `FOR UPDATE` 锁定当前账号、Project 和 Conversation 的这一行，因此只串行同一 Conversation；同一 Project 下的其他 Conversation 可以独立推进。

### storyboard_brainstorm_messages

| 字段 | 说明 |
| --- | --- |
| `id` | 客户端提供的稳定非空 Message ID |
| `user_id`、`project_id`、`conversation_id` | 完整 owner 与父级 scope |
| `parent_id` | 平铺图的父 Message；第一个 User root 可为空 |
| `role` | `user` 或 `assistant` |
| `content` | User Message 的唯一正文事实 |
| `output` | Assistant 的完整有序 JSON 数组；不按 chunk 落库 |
| `status` | `pending/streaming/awaiting_approval/completed/failed/cancelled/interrupted` |
| `revision` | Message CAS 版本；初始为 1，每次成功 Assistant 更新或 continue 递增 |
| `client_request_id`、`request_hash` | 不可变的 append/regenerate 幂等键与规范语义输入 SHA-256 |
| `continue_request_id`、`continue_request_hash` | 最近一次 continue 的独立幂等键与规范语义输入 SHA-256 |
| `created_at`、`updated_at` | 消息创建与更新时间 |

User Message 正文只使用 `content`；Assistant 正文只使用 `output`，避免双重事实。output 只要求是有界 JSON 数组，按原顺序保留 text、tool call、tool result、status、error 等未知 item；具体 item 联合类型由后续任务定义。Conversation 和 Project Memory 列表使用 `page/pageSize` 返回 `{items,total}`；Message 列表按 `created_at ASC, id ASC` 分页返回平铺图，单页可能不包含祖先，客户端需要继续请求其他页。

数据库为 active Assistant 建立 `(user_id, project_id, conversation_id)` 部分唯一索引，只覆盖 `role='assistant' AND status IN ('pending','streaming','awaiting_approval')`，保证同一 Conversation 最多一个 active Turn。非空 `client_request_id` 与 `continue_request_id` 分别建立 Conversation scope 的部分唯一索引，查询同时检查两个命名空间。原始 Turn key/hash 保持不可变，continue 只更新独立字段；相同 key 会比较对应 hash，语义相同返回已有结果，语义不同返回 HTTP 409。相同 Message ID 与相同规范语义输入也返回原 Turn；复用 ID 但输入不同返回 409。

Assistant 更新必须提交 `expectedRevision`，并以 `id + user_id + project_id + conversation_id + revision` compare-and-set：成功时替换完整 output、校验生命周期转换并将 revision 加 1；旧 revision、迟到 completion 或非法转换不能覆盖已经 cancelled、interrupted 或更高 revision 的 Message。冲突返回 HTTP 409，并在可用时通过 `data.current` 返回当前 Message。

append Turn 在一个数据库事务内依次锁定 Conversation、先判断幂等重放和 active 冲突、创建 User Message、创建 pending Assistant Placeholder、更新 `current_message_id`。任何 Message 插入或指针更新失败都会整体回滚。regenerate 不创建新 User Message，而是在同一 User Message 下创建新的 pending Assistant sibling，旧 Assistant 保留。continue 只接受 terminal Assistant，通过 `expectedRevision` 复用原 ID/output，保留不可变的原始 Turn 幂等字段，只写入独立的最新 continue 幂等字段，转回 pending、revision 加 1 并更新当前指针；它不创建 sibling。事务在模型调用或浏览器流式处理开始前提交，不跨网络等待。

### storyboard_memories

| 字段 | 说明 |
| --- | --- |
| `id` | 客户端提供的稳定 Memory ID |
| `user_id`、`project_id` | owner 与父 Storyboard Project scope |
| `kind` | 必填的有界类型字符串 |
| `scope`、`path` | `project/scene/shot`；project 要求空 path，scene/shot 使用稳定实体 ID |
| `content` | 用户已确认的 Memory 正文 |
| `tags` | 有界字符串数组 |
| `source_message_id` | 可选的同 Project 来源 Message |
| `operation_id` | 当前 `user_id + project_id` 内必填且唯一的操作 ID |
| `created_at`、`updated_at` | 创建与更新时间 |

Memory 表只保存已确认记录；候选 Memory、Summary 和运行时 Context 仍不属于持久事实。`source_message_id` 存在时必须属于同一账号和 Project，不能借引用读取其他账号或项目的 Message。

### 所有权与删除

每个 Conversation、Message 和 Memory 读写都先限定当前 `user_id + project_id`，Message 再限定 `conversation_id`。子资源不存在和越权统一返回 404，不能通过猜测子资源 ID 扩大范围。

这些逻辑关系不依赖数据库外键级联。删除 Conversation 时先获取与 Turn 相同的 Conversation 行锁，再删除其 Messages；删除 Storyboard Project 时先锁 Project 与全部 scoped Conversation，再按 owner scope 清理 Brainstorm Messages、Conversations 和 Memories，最后执行既有 Project 与 `user_files` 删除流程。Conversation/Memory 创建先锁 Project，避免并发删除时留下孤儿记录。Project artifact 的对象存储补偿和 best-effort 旧对象清理语义保持不变。

## script_projects、script_conversations 与 script_messages

`script_projects` 保存剧本项目所有权、标题、创作配置、当前会话、乐观锁 `revision`、生成产物内容哈希，以及指向 `user_files` 的产物快照引用。`script_conversations` 保存项目下的独立会话及标题等会话元数据；`script_messages` 按会话保存角色、正文和顺序关系。顶层 `messages` 只是当前会话消息的兼容视图，不作为第二份消息源落库。

项目详情从 PostgreSQL 的会话和消息重建当前对话，并从私有 S3 JSON 恢复 `storySkeleton`、`adaptationStrategy`、`reviews` 和 `scripts`。产物对象使用不可变 Key `scripts/{user_id}/{entity_id}/{file_id}.json`；只有生成产物内容变化时才写入新对象并更新文件引用，纯消息保存复用现有产物文件。项目整体保存和列表页重命名都携带 `expectedRevision`，旧 revision 不能覆盖较新的服务端状态。

脚本项目、会话、消息和文件记录都通过当前认证账号与项目关系做所有权校验。接口只返回重建后的业务数据，不暴露原始 S3 Key；数据库提交失败时补偿删除尚未引用的新对象，项目删除时先清理关联会话、消息和文件记录，再 best-effort 删除对象；对象删除失败时可能留下不可访问的孤儿对象，交由后续生命周期或清理任务回收。

## volcengine_asset_group_bindings

`volcengine_asset_group_bindings` 保存平台账号作用域与火山引擎 outbound 的上游素材分组绑定。`scope_type` 为 `personal` 或 `enterprise`；企业作用域额外记录 `enterprise_id`，所有记录都记录 `user_id` 与 `outbound_id`。四列联合唯一索引保证同一作用域、账号和 outbound 只有一条绑定。

`format`、`project_name`、`group_id` 和 `group_type` 是首次建组时的配置快照。服务端仅使用当前认证账号推导这些作用域字段，客户端提交的企业、用户、分组和项目字段不会改变数据库查询范围。配置项目或格式变化后会重新建立绑定；首次使用时由服务端查询或创建上游分组，再写入本地绑定。

`settings` 表中的 `key = VolcAssetConfig` 保存完整的管理员资产网关 JSON。该行只允许管理员 API 读写；返回前清除 `secret_key` 与 `access_token`，数据库中仍保留真实凭据。火山远端素材本体只保存在上游，平台不把 Action 列表写入个人 `assets`、Canvas 同步或 WebDAV。

## generation_tasks

`generation_tasks` 是第一方生成、兼容生成历史和后台恢复共用的任务事实表。第一方任务使用以下生命周期：

- `queued`：等待平台 worker 认领。
- `running`：已被 worker 认领，包含供应商返回的 `queued`、`running` 和 `processing`。
- `succeeded`、`failed`、`cancelled`：公开终态。
- `pending`：仅供成功结果持久化期间使用的内部结算状态，不对第一方客户端公开。

任务通过 `worker_lease_owner` 和 `worker_lease_expires_at` 支持认领、租约续期与重启恢复。`user_id + client_request_id` 对非空请求 ID 建立唯一约束。

视频任务使用 `billing_mode` 和 `billing_rate` 保存创建时的计费快照：

- `per_call`：`credits` 保存每次调用预扣的算力点。
- `per_second`：`billing_rate` 保存所选分辨率每秒单价，`credits` 保存单价乘任务时长后的预扣算力点。
- `per_credit`：`billing_rate` 保存每个上游 credit 的算力点单价；任务成功后按上游返回的 `credits` 结算，并将实际平台消耗写入任务 `credits`。

企业折扣应用于上述三种模式计算出的本次总积分，`generation_tasks.credits` 和对应 `credit_logs.amount` 均保存折后实际扣除值；`billing_rate` 继续保存模型原始计费单价。

`upstream_credits` 保存供应商响应中的可空 credits。Vidu 未返回该字段时写入 `NULL`；响应审计 JSON 仍显式保留 `"credits": null`，便于使用日志与调用日志区分字段缺失和数值消耗。

模型展示名保存在 `settings` 的公开 `modelChannel.modelCosts[].displayName` 配置中，不写入 `generation_tasks`。任务 API 在读取时按模型配置动态投影 `modelDisplayName`，未配置时回退实际 `model`；实际模型名继续用于渠道路由和上游请求。新写入的 AI 消费、退款流水备注使用同一展示名规则。

## generation_payloads

`generation_payloads` 保存完整命令和脱敏后的上游请求、响应及原始错误。它与任务一一对应，可按保留策略清理；长期任务摘要仍保存在 `generation_tasks.metadata`。

## generation_task_events

`generation_task_events` 是轻量、append-only 的生命周期审计表，不是事件溯源系统；当前任务状态仍以 `generation_tasks` 为准。

| 字段 | 说明 |
| --- | --- |
| `id` | 主键，事件 ID |
| `task_id` | 关联任务 ID，建立索引 |
| `type` | 事件类型，建立索引 |
| `detail` | 小型、脱敏的文本详情 |
| `created_at` | 创建时间，建立索引 |

回调、轮询、重试、超时、取消请求和终态决定可追加事件。不得写入 API Key、回调密钥、data URI 正文或签名 URL 查询参数。

## 终态和退款事务

生成生命周期的业务决策位于 `service/`：包括允许的来源状态、归一化错误、是否退款、退款文案以及终态事件内容。

`repository/` 只执行数据库操作。最终状态写入、用户余额返还、`credit_logs` 退款流水和 `generation_task_events` 终态事件在同一 PostgreSQL 事务中完成。并发 callback、poll、cancel 或 timeout 只有一个 compare-and-set 可以提交终态。

按 credits 计费时，用户余额扣减、任务实际算力点与上游 credits 更新、`credit_logs` 消费流水在同一事务中完成；余额不足时全部回滚并将任务收敛为失败。按次和按秒计费继续在任务创建时预扣。

`credit_logs` 对非空 `task_id + type` 建立唯一约束，防止同一任务重复扣费或退款。
